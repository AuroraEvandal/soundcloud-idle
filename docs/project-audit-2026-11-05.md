## Исправлено в репозитории

### P1. Повтор открытия пака мог повторно списать монеты

Раньше `open-pack` не принимал ID операции. Если база списала 200 монет и выдала
карточку, но ответ потерялся или последующее чтение данных завершилось ошибкой,
повторное нажатие покупало ещё один пак. Клиент не мог получить первый дроп повторно.

Добавлена миграция `20261105162840_idempotent_pack_opening.sql`: приватная таблица
`pack_requests` и RPC `open_pack_idempotent`. Блокировка игрока, списание, выдача и
сохранение результата выполняются в одной транзакции. Повтор ID возвращает прежний
дроп; подмена пака отклоняется. Повтор также не восстанавливает заново использования
карточки, потраченные после покупки. Таблица закрыта RLS, RPC доступен только серверу.

Клиент передаёт `requestId`. Контракт сначала дополнен в `docs/api.md`, раздел 15;
формат ответа сохранён. Старый клиент без ID продолжает работать, но не защищён от
повторной покупки после потери ответа.

Файлы: `supabase/functions/open-pack/index.ts`, новая миграция,
`frontend/frontend/src/api.js`.

### P1. HTTP 500 ошибочно считался подтверждённым отказом операции

`callIdempotent` сохранял ID только после сетевой ошибки. При JSON-ответе
`INTERNAL`/500 он удалял ID. Например, в `record-snippet` SQL-операция может успешно
сохранить энергию и релиз, а последующее `studioView` — упасть. Новый запрос получал
новый ID, и сервер выполнял действие повторно.

Теперь 5xx и `INTERNAL` отмечаются как неопределённый исход (`ambiguous`): ID остаётся
прежним. Студия сохраняет ту же пачку тапов и повторяет её с тем же UUID. Обычные
ошибки валидации по-прежнему сохраняют свои коды и завершают попытку.

Файлы: `frontend/frontend/src/api.js`, `frontend/frontend/src/screens/Studio.jsx`.

## Безопасность и ограничения проверки

В облаке проверенные игровые `SECURITY DEFINER` RPC закрыты для `anon` и
`authenticated`. Отсутствие RLS-политик на 29 таблицах соответствует выбранной
архитектуре: доступ через сервер с `service_role`, прямой доступ браузера закрыт.
Это информационное сообщение советника, а не повод открыть политики всем игрокам.

Советник сообщил избыточный `EXECUTE` на системном помощнике `rls_auto_enable()` для
клиентских ролей. Проверено определение: это `event_trigger`, а не обычная игровая
RPC; обход прав через него не подтверждён. Стоит отозвать лишнее разрешение при
обслуживании базы. [Описание предупреждения Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

Найдены 15 внешних ключей без покрывающих индексов. На маленькой базе это не
блокирует игру; индексы стоит подбирать по нагрузке перед ростом количества игроков.
[Рекомендация Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys).

В репозитории `service_role` не обнаружен как встроенный клиентский ключ; сервер
берёт секреты из окружения. Полноценная проверка Telegram на телефоне, реальной
оплаты Stars, задержек мини-игр и многопользовательской нагрузки не выполнялась.

## Ускорение записи и старта

В логах до исправления (успешные POST в `eu-central-1`): login — в среднем
5137 мс (6 запросов), get-studio — 3339 мс (7), record-snippet — 2868 мс (6).
База проекта находится в `ap-southeast-2`: несколько последовательных обращений
функции из Европы к базе в Австралии складывались в секунды. Клиент добавлял
окно 600 мс и сразу обнулял шкалу, позволяя набрать следующий релиз до ответа.

Теперь функции направляются в регион базы (настраивается через переменную
`VITE_SUPABASE_FUNCTION_REGION`). Получение студии и запись собирают полный
JSON в одном приватном RPC. Необязательная загрузка питомцев не блокирует старт
игры. Очередь отправляет тапы максимум через 250 мс, а при заполнении хайпа — сразу.
Шкала остаётся полной, появляется «Выпускаем сниппет…»; следующий сниппет доступен
после подтверждения и закрытия результата. Монеты и стримы берутся только с сервера.
UUID и недоставленные тапы сохраняются при перезагрузке. Старый GET не откатывает
уже подтверждённую запись.

В изолированном интерфейсе проверены 20 тапов, показ награды, блокировка микрофона
и возврат к следующей записи. Автотесты отдельно проверяют задержанный ответ,
повтор после HTTP 500, перезагрузку и старый GET. В облачной БД проведён SQL smoke
с созданием проверочного игрока и итоговым ROLLBACK: запись, один релиз, повтор
без списания, чтение студии, открытие и повтор пака. История миграций согласована
с именами файлов репозитория. Реальный HTTP подтвердил регион `ap-southeast-2`,
CORS `x-region` и отказ 401 без подписи Telegram.

Это не обещание постоянной задержки: первый HTTP после публикации занял 3841 мс,
следующие неподписанные проверки — 616 и 965 мс. Они проверяют маршрут и авторизацию,
а не время записи с реальным игроком. Холодный запуск, мобильная сеть и точность
тайминга мини-игр требуют проверки внутри Telegram на телефоне.

Beat Lab опубликован с ценой записи 50 энергии (миграция 20261105174148). Проверено: 34 серверных и 25 клиентских тестов, сборка и Deno check. В облаке проверены стоимость и повтор записи в транзакции с ROLLBACK. Интерфейс записи, прослушивания, продажи и стриминга проверен на тестовых ответах.
