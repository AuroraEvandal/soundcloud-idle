Это договор между бэкендом и фронтом. Если нужно что-то изменить, сначала правим этот файл и сообщаем друг другу, потом код.

## Совместимость веток (2026-11-05)

После объединения с `main` применить миграции по порядку, включая
`20261105120000_merge_recording_compatibility.sql` и
`20261105142758_beatmaker_studio_economy.sql`, перед публикацией Edge Functions.
Она сохраняет историю запросов студии, согласует столбцы `snippet_requests` и

## Общие правила

### Межраундовые мини-игры (2026-11-02)

Обновление timing (2026-11-03): нужны три попадания подряд. Этапы: слева направо
за 1200 мс, справа налево за 1000 мс, хаотичный проход за 2100 мс. Цель 40–60%.
Ответ дополнен `server_processing_ms` (время обработки запроса без сети), `timing_hits` (0..3) и `timing_path` (8 сохранённых точек для
третьего этапа). После успешного тапа сервер запускает следующий этап с подготовкой
800 мс и новым `started_at`; `penalty_points` остаётся null до третьего попадания.
Действия timing: `tap-1/2/3`, `timeout-1/2/3`. Повтор ID предыдущего этапа возвращает
текущий прогресс, не засчитывая ещё один тап. Промах/таймаут сразу завершает всю
игру с единственным штрафом 15. Допуск сети для timing сокращён до 80 мс;
сленг и волна сохраняют старые правила. Применить миграцию
`20261103120000_timing_three_hits.sql` вместе с обновлением фронтенда и обеих мини-игровых Edge Functions.
Синхронизация часов вычитает server_processing_ms из RTT: холодный старт функции
не должен ускорять анимацию относительно серверного таймера.

Перед раундами 2 и 3 активного баттла обязательна одна мини-игра. При 2:0 баттл
уже завершён, новой игры нет. Успех даёт 0, провал timing/wave — 15, slang — 20
штрафных очков **следующего** раунда. Итог: `max(0, исходные_очки - штраф)`;
победитель и награды определяются после вычитания. Здоровье и баффы не добавляются.

- `start-mini-game`: `{initData, battleId, roundNumber, actionId: "prepare" | "start"}`.
  `roundNumber` — предстоящий раунд (2/3). Prepare сохраняет случайную игру;
  start запускает её один раз. Повторы не меняют игру, таймер или результат.
- Ответ: `{id, kind: "timing" | "slang" | "wave", round_number, duration_ms,
  started_at, server_now, prompt, options: [{id, text}], penalty_points}`.
  Время — миллисекунды Unix; `started_at: null` до старта,
  `penalty_points: null` до завершения, затем 0/15/20. Правильный ответ не выдаётся.
  Сленговая строка и варианты скрыты до start, чтобы нельзя было заранее решить QTE.
- `finish-mini-game`: `{initData, battleId, miniGameId, actionId}`.
  Для timing `actionId` — `tap-1`, `tap-2`, `tap-3` или `timeout-1/2/3`;
  для wave — `tap`/`timeout`, для slang — ID варианта/`timeout`.
  Очки, success и время тапа клиент не присылает. Ответ того же формата;
  `penalty_points: null` означает незавершённую игру (в том числе успешный
  промежуточный этап timing), 0/15/20 — окончательный сохранённый исход.
- `submit-round` сохраняет прежний запрос. Для раундов 2/3 сервер проверяет
  завершённую мини-игру; иначе `MINI_GAME_REQUIRED`. В `round.player` добавляются
  `base_points` и `penalty_points`, а `points` уже содержит штраф. В `round`
  добавляется `mini_game: {kind, penalty_points, message}` (null в первом раунде).
- Ошибки: `MINI_GAME_REQUIRED`, `MINI_GAME_NOT_STARTED`, `INVALID_MINI_GAME_ACTION`,
  плюс существующие ошибки авторизации, чужого/завершённого баттла и номера раунда.

Рандомизатор `Math.floor(Math.random() * 3)` выполняется на сервере и сохраняется
в БД. Две игры могут совпасть. После start есть 800 мс подготовки; timing состоит из
трёх этапов по правилам обновления выше, slang — 2000 мс, wave — 3200 мс (пики 800/2400 мс,
окно ±240 мс). Проверка использует серверное время получения запроса с допуском
80 мс для timing и 250 мс для остальных игр на сеть после правой границы. Клиент синхронизирует анимацию по server_now.
Таймаут, закрытие приложения и повторный вход не сбрасывают попытку.

Это защищает сумму штрафа, повторное списание и пропуск игры; автоматизированный
клиент всё ещё может посылать tap в известное окно. Задержка сети сверх допуска
может испортить точный тап; необходим плейтест в Telegram на мобильной сети.
Миграцию и две новые функции необходимо развернуть до обновления фронтенда.

- Все функции вызываются через Supabase:
  ```js
  const { data, error } = await supabase.functions.invoke('имя-функции', { body: { ... } })
  ```
- В **каждый** запрос фронт добавляет поле `initData`: `window.Telegram.WebApp.initData`. По нему сервер проверяет, что это настоящий игрок.
- Фронт присылает **только ID** (карточек, батла, соперника). Тексты, оценки и очки всегда считает сервер.
- Все ответы в формате JSON.

### Формат ошибки

Если что-то пошло не так, функция возвращает:

```json
{ "error": { "code": "CARD_NOT_OWNED", "message": "У игрока нет карточки 142" } }
```

| Код | Когда |
|---|---|
| `INVALID_INIT_DATA` | Подпись Telegram не прошла проверку |
| `PLAYER_NOT_FOUND` | Игрока нет в базе (нужно сначала вызвать `login`) |
| `BATTLE_NOT_FOUND` | Нет такого батла или он чужой |
| `BATTLE_FINISHED` | Батл уже закончен |
| `ROUND_ALREADY_SUBMITTED` | Этот раунд уже отправлен |
| `INVALID_ROUND` | Номер раунда не тот, который сейчас активен |
| `INVALID_CARDS` | Не 4 карточки или слоты в неправильном порядке |
| `CARD_NOT_OWNED` | У игрока нет такой карточки |
| `CARD_BURNED` | Карточка сгорела: лимит боёв (3) исчерпан |
| `OPPONENT_LOCKED` | Соперник ещё не открыт (мало популярности) |
| `IDEMPOTENCY_CONFLICT` | `requestId` уже использован с другим содержимым запроса |
| `BATTLE_IN_PROGRESS` | У игрока уже есть активный батл с другим соперником |
| `CARD_POOL_TOO_SMALL` | Для одного из слотов у игрока меньше 4 доступных карточек |
| `INTERNAL` | Ошибка сервера, можно повторить |
| `INVALID_REQUEST_ID` | Не передан корректный UUID для идемпотентного действия |

## 1. `login`

Вызывается при каждом открытии приложения. Находит игрока или создаёт нового.

**Запрос**
```json
{ "initData": "..." }
```

**Ответ**
```json
{
  "is_new": false,
  "player": {
    "id": "b1c2d3e4-...",
    "username": "vasya",
    "avatar": "default",
    "level": 3,
    "xp": 240,
    "xp_to_next": 400,
    "popularity": 120,
    "coins": 350,
    "skills": { "rhyme": 3, "flow": 2, "punch": 4, "charisma": 1 }
  }
}
```

`login` создаёт игрока один раз и выдаёт стартовые карточки. Повторный вызов не сбрасывает прогресс.

`username` берётся из Telegram (`username`, иначе `first_name`, иначе `player`) и **обновляется при каждом входе**, если игрок сменил его в Telegram. Отдельно приложение имя не запрашивает.

## 3. `get-hand`

Карточки игрока для сборки строчки.

> Рука создаётся **сервером**: для каждого слота выбирается ровно 4 случайные карточки из тех, что есть у игрока. Рука запоминается в батле, поэтому `submit-round` принимает только карточки из неё. Эта же рука приходит в ответах `start-battle` и `submit-round`, а `get-hand` нужен, чтобы восстановить экран, если игрок перезапустил приложение посреди раунда.
>
> Правила руки:
> - Выдаются только «рабочие» карточки: поле `uses_left` (осталось боёв до сгорания) больше 0.
> - В раундах 2 и 3 карточки, уже прошедшие в этом баттле, стараются не выдаваться снова; если на слот набирается меньше 4, недостающие добираются из остальных рабочих карточек (могут повториться с ранними раундами).
> - Если между раундами часть карточек сгорела, рука в слоте может быть короче 4.
> - У каждой карточки в ответе есть поле `uses_left`.

**Запрос**
```json
{ "initData": "...", "battleId": "9f8e7d6c-..." }
```

**Ответ**
```json
{
  "battle": {
    "id": "9f8e7d6c-...",
    "status": "active",
    "opponent": { "id": 1, "name": "МС Подвал", "style": "Дворовый, грубоватый", "level": 1 },
    "player_rounds_won": 0,
    "opponent_rounds_won": 0
  },
  "round": { "number": 1, "theme": "деньги" },
  "last_result": null,
  "cards": {
    "setup": [
      { "id": 140, "text": "Ты в бою как нищий — пустой кошелёк", "theme": "деньги", "themes": ["деньги"], "rarity": "common", "syllables": 11, "uses_left": 3 }
    ],
    "development": [
      { "id": 141, "text": "А я на сцене — ты просто игрок", "theme": "деньги", "rarity": "common", "syllables": 10, "uses_left": 2 }
    ],
    "boost": [
      { "id": 143, "text": "Ты копишь на кроссы, я кручу бабки", "theme": "деньги", "rarity": "common", "syllables": 11, "uses_left": 3 }
    ],
    "punch": [
      { "id": 142, "text": "Твой флоу, бро, — домашние тапки", "theme": "ирония", "rarity": "rare", "syllables": 10, "uses_left": 1, "bonus": { "type": "flat_points", "value": 3 } }
    ]
  }
}
```

Также возвращаются `round` (текущий раунд и тема), `battle` (соперник и счёт) и `last_result` (последний отправленный раунд, если он есть; `null`, если ещё нет). Если игрок закрыл приложение после отправки раунда, фронт показывает сохранённый результат и позволяет продолжить. После завершения батла `round` и `cards` равны `null`, а `last_result` содержит финальный результат.

Слоты: `setup` (завязка), `development` (развитие), `boost` (усиление), `punch` (панч).

## 4. `start-battle`

Создаёт батл. Сервер сам выбирает темы для 3 раундов, а фронту отдаёт тему первого.

**Запрос**
```json
{ "initData": "...", "opponentId": 1, "requestId": "UUID" }
```

`requestId` генерируется фронтом один раз на попытку начать батл и повторяется при сетевом повторе. Повтор с тем же ID возвращает тот же батл, а не создаёт второй.

**Ответ**
```json
{
  "battle": {
    "id": "9f8e7d6c-...",
    "status": "active",
    "opponent": { "id": 1, "name": "МС Подвал", "style": "Дворовый, грубоватый", "level": 1 },
    "player_rounds_won": 0,
    "opponent_rounds_won": 0
  },
  "round": { "number": 1, "theme": "деньги" },
  "hand": { "setup": [], "development": [], "boost": [], "punch": [] }
}
```

Одновременно у игрока может быть только один активный батл. Повторный старт с тем же соперником вернёт его состояние; запрос с другим соперником получит `BATTLE_IN_PROGRESS`.

Ошибки: `OPPONENT_LOCKED`, `BATTLE_IN_PROGRESS`, `CARD_POOL_TOO_SMALL`.

## 5. `submit-round`

Главная функция. Принимает собранную строчку, оценивает, возвращает результат.

**Запрос**

`cardIds` строго в порядке слотов: завязка, развитие, усиление, панч.
```json
{
  "initData": "...",
  "battleId": "9f8e7d6c-...",
  "roundNumber": 1,
  "requestId": "UUID",
  "cardIds": [140, 141, 143, 142]
}
```

`requestId` генерируется фронтом один раз для отправляемой строки и сохраняется при сетевых повторах. Повтор того же запроса возвращает сохранённый ответ без повторной оценки и наград. Повторный номер раунда с другим содержимым возвращает `ROUND_ALREADY_SUBMITTED`.

**Ответ (батл продолжается)**
```json
{
  "round": {
    "number": 1,
    "theme": "деньги",
    "player": {
      "lines": [
        "Ты в бою как нищий — пустой кошелёк",
        "А я на сцене — ты просто игрок",
        "Ты копишь на кроссы, я кручу бабки",
        "Твой флоу, бро, — домашние тапки"
      ],
      "scores": { "rhyme": 8.5, "flow": 9, "punch": 7, "meaning": 6 },
      "points": 80,
      "comment": "Панч про домашние тапки смешной и в тему, но первая пара строк слабо связана со второй."
    },
    "opponent": {
      "lines": [
        "Деньги — пыль, я вырос на районе",
        "А ты рос в тепле и на балконе",
        "Я голодным лез на каждый сход",
        "А ты ждал, что мамка принесёт"
      ],
      "scores": { "rhyme": 9, "flow": 8, "punch": 6, "meaning": 7 },
      "points": 75
    },
    "winner": "player"
  },
  "battle": {
    "status": "active",
    "player_rounds_won": 1,
    "opponent_rounds_won": 0
  },
  "next_round": { "number": 2, "theme": "улица" },
  "hand": { "setup": [], "development": [], "boost": [], "punch": [] },
  "rewards": null
}
```

**Ответ (батл закончен)**

Батл заканчивается, когда кто-то выиграл 2 раунда. Тогда `next_round` равен `null`, а `rewards` заполнен:
```json
{
  "battle": { "status": "finished", "result": "win", "player_rounds_won": 2, "opponent_rounds_won": 1 },
  "next_round": null,
  "hand": null,
  "rewards": { "xp_change": 25, "popularity_change": 15, "level_up": false, "new_level": 3 }
}
```

Ошибки: `BATTLE_NOT_FOUND`, `BATTLE_FINISHED`, `ROUND_ALREADY_SUBMITTED`, `INVALID_ROUND`, `INVALID_CARDS`, `CARD_NOT_OWNED`, `CARD_BURNED`, `IDEMPOTENCY_CONFLICT`.

## Изменения в существующем (v0.2, экономика)

- **`player`**: новые поля `streams` (всего прослушиваний) и — там, где менялись монеты или популярность, — всегда свежий `player` целиком.
- **`login`**: новый игрок получает **300 монет** и бесплатный «Бит 1» (куплен сразу).
- **`submit-round`**: в `rewards` при победе добавляется `coins_change: 50` (за поражение `0`). Монеты начисляются сервером там же, где опыт и популярность.
- **`start-battle`**: в `battle.opponent` добавляется `outfit` — случайная одежда соперника, **только для отображения** в арене. Формат: `{ "hat": { "id": 1, "name": "Кепка", "image": "https://.../cap1.png" }, "hoodie": null, "pants": {...}, "shoe": {...}, "chain": null }` (слот может быть `null`). Сервер выбирает один раз на батл из всей библиотеки одежды, включая вещи «только из паков». Бонусов у одежды соперника нет и в расчёты она не входит. Свой внешний вид игрок берёт из `get-wardrobe`.
- **Новые коды ошибок:** `NOT_ENOUGH_COINS`, `ALREADY_OWNED`, `ITEM_NOT_FOUND`, `NOT_OWNED`, `NO_ENERGY`.

## 6. `get-studio`

Запрос: `{}`. Ответ:
```json
{
  "player": { "...": "как в login, плюс streams" },
  "studio": {
    "hype": 12, "hype_max": 20,
    "energy": 80, "energy_max": 100,
    "selected_beat_id": 1,
    "income_pct": 10,
    "beats": [{ "id": 1, "name": "Бит 1: Дрилл", "base_streams": 150, "price": 0, "owned": true }],
    "equipment": [{ "id": 1, "name": "Наушники", "price": 200, "bonus": { "type": "income_pct", "value": 10 }, "owned": false }]
  }
}
```
Энергия восстанавливается временем **на сервере**: +1 за 3 секунды, максимум 100. `income_pct` — суммарный бонус надетой одежды и купленного оборудования.

## 7. `record-snippet`

Оптимизация от 2026-11-05: публичный JSON не меняется. `get-studio` и
`record-snippet` собирают игрока, энергию, каталоги и бонусы внутри одного приватного
RPC после проверки подписи Telegram. Перед публикацией этих функций нужна миграция
`20261105164037_studio_fast_path.sql`.
Клиент отправляет пачку немедленно при заполнении шкалы; до подтверждения показывает
«Выпускаем сниппет…» и не начинает следующую запись. Награда появляется только из
ответа сервера. Остальные тапы объединяются в короткое окно до 250 мс.
Функции игры вызываются в регионе базы (`ap-southeast-2` для текущего проекта);
регион переопределяется через `VITE_SUPABASE_FUNCTION_REGION`.

Запрос: `{ "taps": 17, "requestId": "UUID" }` — тапы, накопленные фронтом за короткое окно (до 250 мс; при полном хайпе — сразу), и уникальный ID операции. `requestId` временно необязателен для совместимости со старым фронтом; новые клиенты должны его отправлять. При сетевом повторе новый фронт сохраняет тот же ID, чтобы сервер не списал энергию и не начислил награду второй раз. Сервер режет `taps` до 200 за запрос, списывает энергию (регенерация считается от серверного времени) и добавляет хайп: каждый тап = −1 энергия, +1 хайп. Когда хайп доходит до `hype_max`, выходит сниппет:

```
streams      = round(base_streams(бита) × (1 + min(popularity, 400) / 200) × (1 + income_pct / 100))
coins        = round(streams / 10)
популярность += min(25, max(1, round(streams / 100 × (1 + popularity_pct / 100))))
```

Ответ: `{ "player": {...}, "studio": {...}, "released": [{ "streams": 150, "coins": 15, "popularity_change": 2 }] }` — `released` может быть пустым массивом.
Ошибки: `NO_ENERGY`.

## 8. `select-beat`

## 10. Beatmaker: запись и продажа битов

Beatmaker — простой двухтактовый секвенсор: барабаны (kick/snare/hi-hat), пианино и мелодия. Это игровой экран без загрузки аудиофайлов. Каждый новый бит тратит 50 единиц общей энергии студии (та же энергия, что расходуется на сниппеты). Сервер проверяет рисунок нот и ударов, считает качество и списывает энергию транзакционно. `requestId` обязателен для всех изменяющих запросов; повтор с тем же ID возвращает сохранённый результат, запрос с другим содержимым даёт `IDEMPOTENCY_CONFLICT`.

### `get-beatmaker`

Запрос `{}` или `{ "before": { "created_at": "ISO timestamp", "id": "UUID" } }` для следующей страницы. Ответ: `{ "player": {}, "energy": 80, "energy_cost": 50, "beats": [...], "next_cursor": null }`. Страница содержит до 100 записей **текущего игрока**, сортировка created_at DESC, id DESC. next_cursor — объект before для следующей страницы либо null. Число записей в базе этим не ограничивается. Сервер возвращает качество, статус, лимит и collectable_streams / collectable_coins. Ошибка некорректного курсора: INVALID_REQUEST.

### `record-beat`

В списке каждый бит также содержит `instant_sale_coins` — текущую гарантированную
цену продажи, рассчитанную сервером. В студии появился экран Beat Lab с двумя
тактами, выбором нот и локальным прослушиванием записанных сэмплов. Черновик рисунка
сохраняется отдельно для каждого игрока; стоимость записи списывается только сервером.

Запрос:

```json
{
  "genre": "trap", "bpm": 140, "key": 0, "scale": "minor",
  "pattern": {
    "drums": { "kick": [0, 8, 16, 24], "snare": [4, 12, 20, 28], "hihat": [0, 2, 4, 6, 8, 10, 12, 14] },
    "piano": [{ "step": 0, "note": 12 }, { "step": 16, "note": 15 }],
    "melody": [{ "step": 4, "note": 19 }, { "step": 20, "note": 17 }]
  },
  "requestId": "UUID"
}
```

`step` — шаг 0–31 в двух тактах; `note` — MIDI-позиция 0–23 в диапазоне секвенсора; `key` — класс ноты 0–11. Новые жанры: `trap`, `plugg`, `cloud_rap` (Trap, Plugg, Cloud rap); лад: `major` или `minor`. BPM 60–180. Старые `drill` и `phonk` остаются допустимыми для сохранённых записей, черновиков и повторов запросов; новые стили не переименовывают существующие записи. Сервер рассчитывает оценку 0–100 из ритма (соответствие BPM и опорным долям стиля), гармонии (ноты в выбранном ладу и созвучие пианино с мелодией), заполненности дорожек и разумной плотности событий. Клиент не присылает оценку. Ответ: `{ "player": {}, "beat": { "id", "quality_score", "score_breakdown", "status": "draft", "..." }, "energy_cost": 50 }`.

Прослушивание использует небольшие локальные WAV-сэмплы выбранного жанра, загружаемые по требованию. Звук не отправляется на сервер; рисунок, стоимость (50 энергии), награды и четыре критерия оценки сохраняются. Перед публикацией клиента применить миграцию `beatlab_genres` и обновить `record-beat`.

### `sell-beat`

Запрос `{ "beatId": "UUID", "requestId": "UUID" }`. Продаёт черновик один раз и сразу начисляет монеты. Выплата: `10 + round(quality_score × 0.2) + floor(min(popularity,400)/40)` монет. Ответ: `{ "player": {}, "beat": {}, "coins_earned": 20 }`.

### `release-beat`

Запрос `{ "beatId": "UUID", "requestId": "UUID" }`. Вместо немедленной продажи выпускает бит на 24 часа стриминга. Популярность открывает более высокие ступени возможной выплаты: `max_tier = min(6, 1 + floor(log2(1 + popularity/100)))`. Качество повышает шанс пройти каждую ступень: `0.10 + quality_score/400` (не выше 0.35). Каждая пройденная ступень удваивает лимит стримов, поэтому вероятность максимума падает экспоненциально. Базовый лимит: `(50 + quality_score × 2) × (1 + min(popularity,400)/400)`, затем умножается на `2^viral_tier`. Ответ включает `viral_tier`, `max_tier`, `max_streams` и `duration_hours`. Результат броска сохраняется.

### `collect-beat`

Запрос `{ "beatId": "UUID", "requestId": "UUID" }`. Забирает накопившуюся долю лимита линейно за 24 часа. Начисляет стримы игроку и монеты по курсу 10 стримов = 1 монета, без потери остатка между частичными сборами. После 24 часов стриминг завершается. Ответ: `{ "player": {}, "beat": {}, "streams_earned": 100, "coins_earned": 10, "streams_remaining": 200 }`.

Ошибки: `INVALID_BEAT`, `INVALID_PATTERN`, `NO_ENERGY`, `BEAT_NOT_FOUND`, `BEAT_ALREADY_PROCESSED`, `BEAT_NOT_STREAMING`, `IDEMPOTENCY_CONFLICT`.

## 15. `open-pack`

Запрос: `{ "packId": 1, "requestId": "UUID" }`. Новый клиент сохраняет один `requestId`
до получения определённого ответа, в том числе после HTTP 5xx. Повтор с тем же ID

- редко (7%) вещь одежды, которой ещё нет.
Дубликат карточки возвращает часть монет: 20 / 60 / 150 по редкости (дубликат всё равно остаётся у игрока, сгоревшая карточка от пака восстанавливается с 3 использованиями).

```json
}
```
или `{ "type": "clothing", "item": { "...как в get-shop..." }, "duplicate": false, "refund": 0 }`.

## Как формируются очки раунда (для справки)

Настройки MVP хранятся в приватной таблице `game_balance` (одна строка `id=true`).
`skill_step=0.02`: каждый пункт рифмы/флоу/панча выше стартового 1 добавляет 2%
к вкладу соответствующего критерия; смысл не меняется. `charisma_step=0.01`:
каждый пункт харизмы выше 1 и бонус харизмы надетой одежды добавляет 1% к сумме
критериев. Каждый множитель ограничен `max_skill_bonus=0.5` (не больше +50%).
Бонусы карточек прибавляются после множителей. При стартовых навыках 1 и без
одежды результат прежний. Сырые оценки по-прежнему 0..10. Сервер читает настройки;
клиент не присылает навыки, бонусы или очки.

Пак сначала выбирает редкость с весами `common_weight/rare_weight/epic_weight`
из той же таблицы (70/24/6), затем случайную карточку этой редкости, предпочитая
ещё не полученные. Дубликат возможен, даже если в других редкостях есть новые карты.
Если в каталоге нет карточек выбранной категории, веса распределяются между
существующими категориями. Настройки меняются численно в Supabase без изменения кода.
Нужна миграция `20261105164819_configurable_battle_and_pack_balance.sql`.

```
при стартовых навыках: итог = (рифма × 0,25 + флоу × 0,25 + панч × 0,30 + смысл × 0,20) × 10 + бонусы карточек
```

ИИ-судьи в MVP нет — все критерии считает код на сервере:

- **рифма** — сравнение звуков окончания строки, а не букв: последняя гласная + согласный хвост, глухие/звонкие согласные считаются одним звуком (п≡б, т≡д, к≡г, с≡з, ф≡в), вставные м/н/л/р не ломают рифму (ап/амп), латиница переводится в русские звуки (up→«ап»), совпадение второй от конца гласной и согласных между ними даёт «богатую» рифму (низко/близко, тапки/бабки). Проверяется тестом: `node supabase/tests/rhyme.test.mjs`. Разница длин строк штрафуется относительно длины короткой строки: слоги равны — без штрафа, разница 1 — минус 0,5 балла, дальше по формуле `2×(diff−1)/min` (максимум −50%): 10/11 почти не режет балл, 4/6 — сразу минус 5;
- **флоу** — алгоритм;
- **панч** — из свойств карточки в слоте «панч»: базово по редкости (common 5, rare 7, epic 9), +0,5 за каждый пункт бонуса, максимум 10;
- У карточки есть прежнее поле `theme` и новое поле `themes` — массив из 1–3 тематик. `themes` возвращается дополнительно; если карточке задана только одна тема, массив содержит её же.
- **смысл** — для каждой пары карточек сравниваются все сочетания их тематик, затем каждая тема карточки сравнивается с темой раунда. Результат — среднее по всем таким сравнениям через `theme_relations`. Одинаковые темы дают 10, пары без записи — нейтральные 5.
- **комментарий** («comment») собирается из шаблонов по сильной и слабой стороне строчки.

Количество оценок в день не ограничено. Фронту знать формулу не нужно.

## Принятые решения

- **ИИ-судьи в MVP нет.** Все четыре критерия (рифма, флоу, панч, смысл) считает код на сервере; панч — из свойств карточки-панча, смысл — из таблицы связей тем `theme_relations`. Дневной лимит оценок отменён.
- **Поле `ai_requests_left` устарело и удалено из ответов.** Фронт должен перестать показывать счётчик «оценок осталось». (Код ИИ-судьи сохранён в `supabase/functions/_shared/scoring.ts` выключенным — на случай возврата ИИ после MVP.)
- **Рука:** ровно 4 карточки на каждый слот, выбираются случайно из карточек игрока. Карточка не может оказаться в двух слотах (каждая карточка создана под свой слот).
- **Лимит карточки:** 3 боя. Каждый батл, в котором карточка прошла хотя бы в одном раунде, списывает с неё одно использование. Когда использования кончаются, карточка «сгорает»: остаётся в колоде игрока (видна как сгоревшая), но больше не выдаётся в руку. Восстановления пока нет — новые карточки добавляются контентом (стартовый набор / будущие паки).
- **Нехватка карточек:** если при старте баттла на какой-то слот меньше 4 рабочих карточек — `CARD_POOL_TOO_SMALL`. В середине баттла рука может быть короче 4, но не меньше 1 (софт-лок внутри баттла исключён).
- **Опыт для следующего уровня:** `round(100 × 1.1^(level − 1))`. Уровень 1 → 100, уровень 2 → 110, уровень 3 → 121, уровень 4 → 133 и т.д.
- **Хранение опыта:** поле `xp` в `players` это опыт **внутри текущего уровня**. При повышении лишний опыт переносится на следующий уровень.
- **Победа в батле:** +25 опыта.
- **Поражение в батле:** −10…15 опыта (случайно). Опыт не уходит ниже 0, уровень не понижается.
- **Бонус к опыту** можно будет прокачивать позже (не в MVP).
- **Покупка карточек:** не в MVP, функция не нужна.

- **Два отдельных числа:** опыт (`xp`) даёт уровни, популярность (`popularity`) открывает локации и соперников.
- **Популярность (черновик, можно менять):** победа +15, поражение −5…10. Ниже порога уже открытой локации не падает, чтобы локации не закрывались обратно.

### Экономика (v0.2)

- **Валюта одна — монеты.** Кристаллы и донат — после MVP.
- **Источники монет:** сниппеты и биты в студии, победа в батле (+50, зафиксировано в AGENTS.md «Принятые числа»).
- **Старт:** 300 монет, бесплатный «Бит 1».
- **Студия:** энергия 100, +1 за 3 секунды; `hype_max` = 20 тапов на релиз; за запрос `record-snippet` принимается 1…200 тапов, сервер режет по энергии. Регенерация и всё начисление — только на сервере, времени клиента фронт не предлагает.
- **Формула релиза** — см. `record-snippet`. Множитель популярности ограничен `×3` (после 400 фанатов не растёт), прирост популярности за релиз — не больше +25, чтобы доход не разгонялся бесконечно.
- **Биты** (base_streams → цена): Дрилл 150 → бесплатно; Трэп 300 → 800; Фонк 500 → 2500; Хедлайнер 800 → 6000.
- **Оборудование** (цена → бонус к доходу сниппетов): Наушники 200 → +10%; Микрофон 600 → +20%; Звуковая карта 1500 → +30%; Мониторы 3500 → +50%. Суммарно до +110%.
- **Пак «Базовый»:** 200 монет; 93% карточка (common 70 / rare 24 / epic 6, сначала некупленные в выбранной редкости), 7% одежда; дубликат карточки возвращает 20 / 60 / 150 монет.
- **Целевой темп:** первый пак (200) — за ~10–15 минут активной тапки в студию на старте (~15 монет/мин); с ростом популярности и битами темп растёт.
- **Сходимость со сгоранием карт:** списывается по одному использованию каждой разной карточки за батл: до 8–12 использований, эквивалент до 2,67–4 полных карточек. Пак даёт 3 использования одной карточки; 7% одежды не пополняют колоду. Утверждение об окупаемости требует плейтеста, цены и награды пока не менялись.
- **Оффлайн-дохода нет** (решение: только активная игра). Энергия восстанавливается и оффлайн — это единственный «пассив».

## Питомцы и кейсы (2026-11-04)

Сервер владеет коллекцией, уровнями, дружбой, бонусами и розыгрышем. Один активный питомец.
`get-pets` {} → {pets:[{id,name,level,friendship,friendship_stage,income_pct,owned}],active_pet_id,income_pct}; level=0 для неоткрытых, 1..3 для открытых. friendship=0..60; stage=1/2/3 при 0/20/60. income_pct=level + stage - 1 у активного. `equip-pet` {petId: string|null} → тот же ответ; только принадлежащий игроку. Ошибки NOT_OWNED/ITEM_NOT_FOUND.
Первый дроп: уровень 1, два следующих дубликата: уровни 2/3; после уровня 3 компенсация 300 монет. Дружба отдельно: +1 за релиз, +3 за завершённый баттл любого исхода, только активному на момент события, максимум 60; без повторного начисления при повторе запроса. Бонус только к доходу сниппетов, не оценкам баттлов. Питомцы soundity/micity/scalevillity равновероятны внутри дропа.
`get-cases` {} → {cases:[{id,name,price_stars,pet_chance,available_at}],pets}; free: раз в 24 часа, pet_chance=0.0005; underground:29 Stars/0.01; gift-vault:100 Stars/0.03. При отсутствии питомца кейс выдаёт монеты: free=25, underground=150, gift-vault=600. Это новый состав кейсов вместо демонстрационных концептов.
`open-case` {caseId:'free',requestId:UUID} → {player,drop:{type:'pet'|'coins',pet_id?,level?,duplicate?,refund?,coins?},pets}; выдача и кулдаун атомарны, повтор requestId возвращает сохранённый результат. Ошибка CASE_COOLDOWN.
`create-case-invoice` {caseId:'underground'|'gift-vault',requestId:UUID} → {invoice_url,order_id}; Telegram Stars XTR. Выдача платного кейса только после проверенного successful_payment на сервере; не из callback браузера. `get-case-order` {orderId:UUID} → {status:'pending'|'paid',player?,drop?,pets?}; только свой заказ. Webhook проверяет X-Telegram-Bot-Api-Secret-Token, валюту, цену, владельца и уникальный charge_id. Повтор оплаты не выдаёт второй дроп. Ошибки PAYMENT_UNAVAILABLE, INVALID_REQUEST, ORDER_NOT_FOUND.
Новые маршруты всегда реальные: без Supabase показывается недоступность, не подставляется фейковая коллекция.
`record-snippet` принимает дополнительный `requestId: UUID` для нового клиента: повтор возвращает сохранённый ответ без второго списания энергии/релиза/дружбы. Старый клиент без requestId остаётся совместимым (каждый запрос считается новым действием).
В каждом элементе `get-cases.cases` также возвращается `fallback_coins` — гарантированная награда монетами, если питомец не выпал; интерфейс показывает её до оплаты.
