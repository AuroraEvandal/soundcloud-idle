## Настройка проекта

1. В Supabase создай проект и выполни `backend/schema.sql` в SQL Editor.
2. Выполни `backend/seed.sql`, чтобы добавить карточки, темы, стартовую колоду и каталог одежды.
3. Установи Supabase CLI и выполни `supabase login`, затем `supabase db push --remote=<ID_ПРОЕКТА>` (CLI v3 по умолчанию работает локально).
4. Добавь секрет `TELEGRAM_BOT_TOKEN` в Supabase Secrets. Ключи OpenAI для MVP не нужны — ИИ-судьи нет, оценки считает код.
5. Разверни функции командой `supabase functions deploy --remote=<ID_ПРОЕКТА> --use-api`.
6. Добавь во фронтенд `.env` адрес проекта и только публичный `anon`-ключ:

   ```env
   VITE_SUPABASE_URL=https://<ID_ПРОЕКТА>.supabase.co
   VITE_SUPABASE_ANON_KEY=<ПУБЛИЧНЫЙ_ANON_КЛЮЧ>
   ```

Ключ `service_role` не добавляй во фронтенд. Edge Functions используют серверный секрет Supabase и проверяют подпись Telegram `initData`.

## Что реализовано

### Питомцы и кейсы (2026-11-04)

1. После предыдущих миграций применить `supabase/migrations/20261104120000_pets_and_cases.sql`.
   Она сама добавляет каталоги трёх питомцев и трёх кейсов; повторный seed не нужен.
   Для новой базы также сначала нужны `schema.sql`, `seed.sql` и все миграции по порядку.
2. Развернуть `get-pets`, `equip-pet`, `get-cases`, `open-case`, `create-case-invoice`,
   `get-case-order`, `telegram-payments-webhook` и обновлённые функции студии/гардероба:
   общий `_shared/studio.ts` теперь читает бонус питомца и восстанавливает энергию через RPC.
   Проще развернуть все функции одной командой `supabase functions deploy --use-api`.
3. В Supabase Secrets сохранить `TELEGRAM_BOT_TOKEN` и случайный
   `TELEGRAM_PAYMENT_WEBHOOK_SECRET` (1–256 символов A–Z, a–z, 0–9, `_`, `-`).
   Без обоих секретов создание платного счёта отвечает `PAYMENT_UNAVAILABLE`.
4. Для этого же бота вызвать официальный Telegram `setWebhook`: `url` =
   `https://<PROJECT_REF>.supabase.co/functions/v1/telegram-payments-webhook`,
   `secret_token` = тот же серверный секрет, `allowed_updates` = `["message","pre_checkout_query"]`.
   Проверить `getWebhookInfo`: правильный URL, нет последней ошибки, очередь не растёт.
   У бота один webhook: если бот уже получает сообщения на другом сервере, нужно сначала
   объединить обработчики; замена URL отключит прежнего получателя. Не публиковать токен,
   секрет или полный URL запроса Bot API в логах/скриншотах.
5. Проверить в тестовом окружении Telegram Stars: создание счёта, отмену, реальную
   оплату, доставку после закрытия Mini App, повтор доставки webhook и перезапуск приложения.
   После `successful_payment` в `case_orders` должны появиться `paid`, уникальный
   `charge_id`, сохранённый результат; баланс/питомец меняются один раз. Дубликат оплаты
   с другим charge_id того же заказа отклоняется, требует проверки и возврата оператором.

Клиент не подтверждает оплату: выдачу выполняет только секретом защищённый webhook,
проверяющий владельца, XTR и сумму заказа. Pre-checkout подтверждается только для своего
неоплаченного заказа. Хранится `telegram_payment_charge_id` для поддержки/возврата через
Telegram `refundStarPayment`. Перед приёмом реальных платежей бот должен предоставлять
условия покупки и поддержку `/paysupport`; обработку этих команд должен выполнять
действующий бот (текущий webhook реализует только оплату, остальные обновления пропускает).
Основание: [Telegram Stars](https://core.telegram.org/bots/payments-stars),
[Bot API payments и webhook](https://core.telegram.org/bots/api).

Питомец получает дружбу только через вставку сохранённого релиза и переход баттла
`active → finished`. Экипировка, награда кейса, кулдаун и доход релиза блокируют строку
игрока на время транзакции. Новый клиент присылает `requestId` при записи тапов: повтор
того же запроса возвращает сохранённый результат без повторного расхода/релиза.
Старый клиент без `requestId` работает, но его сетевой повтор считается новым запросом.
Повтор бесплатного кейса и проверка оплаченного заказа возвращают сохранённый дроп
вместе с текущим балансом и коллекцией. Все новые таблицы закрыты RLS; функции доступны
только `service_role`, а Edge Functions проверяют Telegram initData.

Проверки: `npm test` в `supabase/` запускает реальные SQL-миграции в PGlite, включая
дубликаты, лимиты дружбы, доход, кулдаун, идемпотентность и валидацию суммы/владельца.
Это локальная проверка Postgres, а не доказательство развёртывания или реальной оплаты.

### Межраундовые мини-игры

Перед раундами 2/3 — timing, slang или wave. Провал уменьшает очки следующего
раунда на 15/20/15; успех не даёт бонусов. Результат, таймер и выбор игры сохраняются
сервером. Перезагрузка и повторы запросов не дают новую попытку.

Порядок обновления существующего проекта:
1. Применить `supabase/migrations/20261102120000_inter_round_mini_games.sql`, затем
   `supabase/migrations/20261103120000_timing_three_hits.sql` после
   предыдущих миграций. Она обновляет `submit_round_atomic` с сохранением наград.
2. Развернуть `start-mini-game`, `finish-mini-game` и `submit-round` (в последнюю
   входит обновлённый обработчик кодов ошибок из `_shared/common.ts`).
3. Опубликовать новую сборку `frontend/frontend`.

Миграция требует прохождения мини-игр и в уже активных баттлах перед раундами 2/3,
поэтому обновление фронта и функций нужно проводить вместе, в окно обслуживания.
Старый фронт после миграции не сможет отправить раунд 2/3.

Локальная проверка SQL: в `supabase/` выполнить `npm ci`, затем `npm test` (Node 24;
для Node 22 нужен `--experimental-strip-types` для старого теста рифмы).
Тесты запускают настоящие миграции в изолированном PGlite, не обращаясь к облачной БД.
Сборка UI: `npm run build` в `frontend/frontend`.

### Проверка полного флоу мини-игр

Лог `.playwright-cli/console-2026-11-02T15-09-08-031Z.log` относится к UI-проверке
с подменёнными ответами, а не к проверке развёрнутого Supabase:
- `ERR_CONNECTION_REFUSED` — запрос ушёл на тестовый адрес `127.0.0.1:54329`
  до установки Playwright-перехвата; сервера там не было.
- `ERR_FAILED` у finish — намеренный `route.abort()` для проверки повторного запроса.
- 400 у start — тестовый ответ `INVALID_ROUND`. Перехват всех `/functions/v1/**`
  оставался установлен и подменял также login. Это не доказательство ошибки авторизации.
  Реальный `_shared/common.ts` возвращает 401 `INVALID_INIT_DATA` при пустых/неверных
  данных Telegram. Подключение Telegram JS в обычном браузере не выдаёт подписанный initData.

Браузерные скрипты в `output/playwright/` проверяют UI с фикстурами. Перехватывать
нужно только два mini-game endpoint и снимать свой обработчик в `finally`.
Для проверки API без сети: `node --test tests/*.test.mjs` в `frontend/frontend`;
он проверяет реальный `api.js`, payload, коды ошибок и одинаковое действие при повторе.
SQL-проверки выше проверяют настоящие миграции, но не HTTP/Telegram-подпись.

Для проверки всей цепочки нужны:
1. Доступный Supabase со схемой, seed и всеми миграциями, включая
   `20261102120000_inter_round_mini_games.sql` и `20261103120000_timing_three_hits.sql`.
   Развёрнутые функции должны соответствовать этой версии фронта.
2. `TELEGRAM_BOT_TOKEN` именно запускающего бота в серверных Secrets;
   URL этого проекта и его публичный anon-ключ во фронте. `local-test-public-key`
   и незапущенный порт 54329 подходят только для UI-перехвата.
3. Свежий запуск Mini App из бота, с непустым подписанным `Telegram.WebApp.initData`.
   Чистая браузерная сессия без `page.route`, подмены fetch и моков API.
4. Пройти `login → start-battle → submit-round(1) → start-mini-game(prepare/start)
   → finish-mini-game → submit-round(2)`, при необходимости повторить для раунда 3.
   Использовать battleId/id из ответов сервера и текущий номер раунда.
   Для timing нужны `tap-1/2/3` (либо `timeout-N`); успешные первые два этапа
   возвращают `penalty_points: null`, после третьего — 0; промах даёт 15.
5. Проверить успех/провал всех трёх игр, повтор того же finish после потери ответа,
   перезагрузку и `get-hand`, вычитание штрафа ровно один раз перед выбором победителя,
   отсутствие новой мини-игры после 2:0 и однократную выдачу наград.
   В Table Editor проверить `battle_mini_games`, `rounds`, `battles`, баланс игрока.

При ошибке сохранять endpoint, HTTP-статус и JSON `error.code` из Network,
без initData, заголовков авторизации и ключей. Одного console-лога с числом 400
недостаточно, чтобы отличить неверный номер раунда от ошибки другого обработчика.
Точность timing отдельно проверить в Telegram на телефоне и мобильной сети.

shortcut: тайминг проверяется по серверному времени с допуском на сеть 80 мс для рэп-тайминга и 250 мс для остальных;
после плейтеста на мобильной сети пересмотреть окна, если задержки вызывают промахи.
Скриптованные тапы в известное окно этим механизмом не предотвращаются.

- Баттлы: `login`, `get-profile`, `get-hand`, `start-battle`, `submit-round`.
- Студия: `get-studio`, `record-snippet`, `select-beat`.
- Магазин и гардероб: `get-shop`, `buy-item`, `get-wardrobe`, `equip-item`, `buy-beat`.
- Пак и колода: `open-pack`, `get-deck`.
- Старт батла и выдача руки выполняются транзакционно в Postgres. У игрока может быть только один активный батл.
- `submit-round` атомарно записывает результат, меняет счёт и выдаёт награды. Повтор того же `requestId` возвращает сохранённый JSON без повторной награды.
- `get-hand` возвращает текущий раунд, руку, счёт и последний результат, поэтому фронт может восстановить батл после перезапуска.
- Все четыре критерия считаются кодом на сервере, ИИ-судьи в MVP нет: рифма и флоу — алгоритмы, панч — из редкости и бонуса карточки-панча, смысл — из таблицы связей тем `theme_relations` (заполняет автор игры; пока таблица пустая, смысл выходит нейтральным). Код вызова OpenAI сохранён в `_shared/scoring.ts` выключенным. Лимит оценок в день отменён.

Контракт всех перечисленных функций описан в `docs/api.md`. Production-фронтенд уже вызывает сервер на всех экономических экранах. Моки разрешены только в dev; отсутствие конфигурации в production приводит к ошибке, а не к фейковому прогрессу.

## Одежда (косметика)

Таблицы готовы и совпадают с наброском из `API-PROPOSAL.md`:

- `clothing` — каталог вещей (слот, редкость, цена, картинки, бонус);

Каталог заполняется из `backend/seed.sql` (9 вещей, те же id, что в мок-каталоге фронта). Для уже созданной базы таблицы добавляет `supabase/migrations/20261025_clothing.sql`. Функции магазина и гардероба реализованы и описаны в `docs/api.md`.
